# Android: run a robot against independent OneBot services

**Boundary:** a managed binding starts a built-in *runtime worker*, not a protocol service. Start the authorized QQ/Bilibili protocol service separately on the phone (or use an operator-managed loopback tunnel). The APK does not authenticate to Bilibili, manage Bilibili cookies, embed a Bilibili plugin, or install/start third-party executables. Container liveness is not account liveness.

## Operator path

1. Provide a working compatible rootfs with Node >=22.19, `/input/agent-app` (including its matching installed dependencies), and the updated runtime sources. In an offline rootfs build workspace, `node scripts/stage-android-binding-runtime.mjs` stages a **new directory under `.tmp`**, containing `input/agent-app/src` and a per-file SHA-256 inventory. Incorporate its `input/` tree into a *new build copy* of the rootfs, leaving the legacy image intact. The script neither modifies an existing rootfs nor contacts any device. It stages only `.js`/`.mjs` source, no dependencies, data, native platform protocols, auth, or private configuration. Build and test the resulting target-architecture image separately. An APK upgrade alone does **not** upgrade `/input/agent-app`; absent `src/binding-supervisor.mjs` is reported as `runtime_missing` rather than silently falling back to QQ.
2. In the phone bot's binding editor, choose platform, exact numeric self account ID, separate credential-free HTTP and WS URLs (`127.0.0.1` with explicit non-default port), and memory mode. Supply the protocol service's **OneBot bearer**, not its upstream login material. Save each binding. A Bili-only bot needs no QQ login. For an existing QQ-only production install, the `whale-1` builtin with its implicit QQ placeholder continues to use the old login/agent path. The legacy automatic start is suppressed in a mixed registry; modern start is always explicit.
3. Prepare the container, then start the bot. At cold start all bindings require a session bearer and complete metadata; one missing bearer deliberately prevents startup. Endpoint reachability is checked by individual workers after spawn. Re-enter bearers after app-process death or service teardown; after endpoint/account changes, the old bearer cannot be reused for the new target. Stop affects this bot's owned runtime, not its protocol services or other bots. A `custom` runtime is shown as **external**: the operator configures its standard OneBot connections and controls that process outside the APK. No custom command execution or remote lifecycle claim.
4. New bot configuration, if provided, belongs to `/agent/data/bots/<botId>/config.json`. The Android adapter never copies the active legacy runtime's provider secrets; if absent, the runtime uses its own defaults. Identity verification alone does not enable autonomous replies or grant access to a conversation. Binding-scoped allowlists, provider setup, model credentials, and action grants are separate runtime concerns. The mobile registry carries no Bili tool grants. Changing a binding or robot config requires stopping and restarting the managed bot. Global legacy dashboard/config data is not a modern bot's dashboard.

## Diagnostic contract

- Android reads the real private `files/bots.json` (not a demo fixture). The Java host passes one selected persisted bot plus scoped bearer map via a pipe to `/opt/whale/binding-host.mjs`. Node projects an allowlist to `/opt/whale/bindings/<botId>/manifest.json` by atomic rename. Bearer **values** never enter the manifest, status, shell commands, argv, intent extras, logs, or registry. Only the supervisor receives selected bearer environments; each worker gets one. Runtime stdout/stderr from this new launch path is not sent to Android's debug logs. Like any environment credential, these are not protected from root/a debugger or trusted same-UID code.
- Android native start/stop APIs are local to the app's private service. Read-only loopback `GET /bindings?bot=<id>` reports the same filtered view as the UI, not raw runtime files. A `verified` row requires a live owned process, matching start nonce, heartbeat <30s, unchanged selected registry rows and matching platform + self ID. `running` describes only the host; `stale`, `stopped`, `failed`, `runtime_missing`, `external`, `container_required`, `credentials_required` are **not** online. No previous generation's positive status is replayed. Loopback is shared by Android apps: legacy `/exec` and `/raw` are disabled unless a debuggable build has an explicit private `allow-legacy-debug-shell` marker AND a legacy-only registry. Do not enable the debug shell in normal use.
- Distinct binding endpoints and worker console ports are required. Console ports are chosen using temporary loopback listeners; the kernel cannot promise availability between reservation release and worker listen. Collision/worker failure is not treated as success. Android process death can leave proot descendants depending on platform behavior: an orphan's heartbeat is not accepted as owned, and singleton conflicts should be resolved by the operator (do not globally kill other bots). No unattended modern restart, token persistence, cloud discovery, automatic installation or protocol-service supervision is promised.

## Reproducible local evidence

`node --test test/android-binding-host.test.mjs` covers Bili-only and mixed projection, the actual runtime `loadBot` contract, isolated worker credentials, invalid endpoints/accounts, rejection of cookie-shaped input and a real subprocess launch from the host adapter. `node scripts/stage-android-binding-runtime.mjs` is a source staging operation, **not** an install. `android/build.ps1 -AndroidSdk <local-sdk> -OutDir <local-output>` builds a debug APK; its three script assets are copied into a booted rootfs by the service. No Android hardware or emulator, real QQ/Bili account, production network, login, or device deploy is part of these tests.
