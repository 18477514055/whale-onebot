# 2026-11-24 系统级缺陷与架构设计对齐问答报告

> **编制说明**：设备离线期间，全面打磨项目核心链路。本项目不只是表面代码 Bug，还存在多处「上下游设计不合理导致流程必然失败」的结构性断链。
> 本报告基于全仓源码审计、静态依赖扫描及自动化校验脚本（`scripts/verify-local-health.py`），整理出 6 大核心设计缺陷与修复对齐问题，供决策落地。

---

## 一、六大设计缺陷与源码实证

### 1. 【核心生命周期断链】新机核心下载入口死锁 + APK 内置 `core.zip` 成为孤儿资产
- **源码实证**：
  - `android/app/src/com/whaleonebot/ui/EnvConfigScreen.java:120`：将「下载内置核心」移至 `shell.pushVersion()`。
  - `android/app/src/com/whaleonebot/ui/VersionScreen.java:99, 557`：页面中两个按钮全部分流至 `shell.corePage("versions", null)`（只展示已有核心，没有下载创建入口）。
  - 全仓 `grep` 显示 `corePage("download")` 调用点已全部为 **0**。
  - `android/app/assets/bundled/core.zip`（2.26 MB）已打入 APK，但 `BundledEnvironment.java` 只释放了 `environment.bin`，全仓 Java 代码 **0 处引用 `bundled/core.zip`**。
- **后果**：新用户装好 APK 进版本管理页发现无处可下核心，即便 APK 内部已经携带了核心压缩包也完全无法离线解压使用。

### 2. 【通信架构脱节】内置环境扫码出码后，点击「连接 QQ」无协议端响应
- **源码实证**：
  - `ContainerService.java:195`：明确拦截了 `ACTION_BOT`（`if (ACTION_BOT.equals(action) && managedImage) return;`），且内置环境不释放 `container-bot.mjs`。
  - `InstalledRuntimeHost.java:49` 及 `binding-host.mjs:25-27`：受管机器人实例启动��，要求槽位具备有效的 `httpUrl` 与 `wsUrl`（以及 token）。
  - `BotRegistry.java:localQqSlot`：本机 QQ 槽位的 `httpUrl` / `wsUrl` 均为空。
- **后果**：在 `com.whaleonebot.beta` 上扫码成功并保存登录凭据后，点击「连接 QQ」，后台由于没有拉起本机 OneBot 协议端且没有回环地址，受管宿主根本无法与 QQ 通信，连接必然超时或停摆。

### 3. 【解包器防御缺失】`QqClientInstaller.java` 易致 1.2GB 空间永久泄漏与流程崩溃
- **源码实证**：
  - `QqClientInstaller.java:85-92`：遇到 `data.tar.gz` 格式时，先无条件执行 `busybox xz -dc`（xz 解 gzip 必报 exit 1 失败中断）。
  - `QqClientInstaller.java:70-110`：整个 1.2GB 解包过程缺乏 `try ... finally { cleanup(); }` 保护。若解压中途因内存不足被系统杀掉或用户杀后台，`qq-data.tar` 和 `qq-x/` 将永久残留在私有存储，用户无法清理。
  - `QqClientInstaller.java:57`：若用户在全新安装后未先点过「启动容器」，`files/bin/busybox` 不存在，直接抛异常拒绝安装。
  - `QqClientInstaller.java:144, 163`：命令执行只丢弃 stdout，完全不捕获 stderr，一旦失败用户只能看到空泛的 exit 码。

### 4. 【启动性能与系统开销设计不当】启动容器时无条件覆盖 525 个 `.so` 与 fork 风暴
- **源码实证**：
  - `ContainerService.java:383-386`：在受管环境下，每次 boot 都会枚举 `assets/native/gui` 下的 525 个文件（共 138.77 MB）强行 `extractAssetAlways` 覆盖写入并 fork 525 次 `/system/bin/chmod` 子进程。
  - 发生任何 IO 错误使用 `catch (Exception ignored)` 吞掉，无任何 logcat 输出。
- **后果**：即便之前已经释放过，每次启动前台服务都要无端耗费数十秒甚至数分钟磁盘 IO 与 CPU 时间，导致用户看到「容器启动大半天」的卡顿假象。

### 5. 【系统设计与交互规范割裂】13 个文件存在 41 处原生系统黑框 AlertDialog
- **源码实证**：
  - `CoreManagerScreen.java`（5 处）、`VersionScreen.java`（2 处）、`SettingsScreen.java`（2 处）、`BiliPlatformScreen.java`（6 处）、`RuntimeUiEditor.java`（5 处）等大量使用 `new AlertDialog.Builder(activity)`。
- **后果**：弹出的原生对话框不仅样式破坏了项目沉浸式暗色玻璃质感（`Theme.java` / `DESIGN_SYSTEM.md`），且在 Android 13/14 某些定制系统（如 HyperOS）中容易被系统弹窗限制拦截或丢失按键回调。

### 6. 【硬编码绝对路径技术债】`loader.node` 依赖开发机路径补丁违反 P3 原则
- **源码实证**：
  - `loader.node` 动态依赖中硬编码了 `/mnt/d/qq-onebot/.tmp/native-host-arm64-0wfTF4/libonebot-node-host.so`。
  - `ContainerService.java:374` 在手机容器内部伪造了这一全路径目录并写入 `.so`，以补偿 dlopen 失败。
- **后果**：典型的违反根本原则 P3（不许用补偿层遮症状）。手机环境被迫感知开发机路径，日后维护极其脆弱。

## 二、修复与打磨对齐方案（问答与决策选项）

### 议题 1：核心生命周期与离线可用性
- **问题**：全仓 `corePage("download")` 零引用导致无法创建新核心，且 APK 打包的 `core.zip` 未被利用，如何理顺？
- **选项 A（推荐）**：
  1. 启动应用或检测到 `core-instances` 为空时，自动将 APK 内置的 `assets/bundled/core.zip` 释放并注册为一个可用内置核心，��现真正的「零下载开箱即用」；
  2. 在 `VersionScreen.java` 的「内置核心版本」一栏补上「下载更多核心」入口，连通 `corePage("download")`。
- **选项 B**：仅在 `VersionScreen` 补回下载入口，删掉 APK 里的 `core.zip` 以瘦身 2.3MB。
- **选项 C**：仅做内置 `core.zip` 首次自动释放，全面移除在线下载核心功能。

### 议题 2：内置环境下 QQ 协议端与受管容器的生命周期架构
- **问题**：内置环境扫码后点「连接 QQ」，协议端到底应如何被启动与管理？
- **选项 A（推荐）**：统一协议端为容器内受管服务。内置环境扫码登录就绪后，启动本机 OneBot 协议端进程监听 `127.0.0.1:13800`（带瞬时 token），并把该连接配置自动注入宿主管理器，与 B 站协议端架构规范完全对齐。
- **选项 B**：让内置环境继续沿用旧版 `container-bot.mjs` 模式，移除 `ContainerService.java:195` 对 `ACTION_BOT` 的拦截。
- **选项 C**：完全剥离协议端，强制要求用户在外部运行 OneBot 服务通过填 URL 连接。

### 议题 3：`QqClientInstaller` 解包鲁棒性与���常防护
- **问题**：解包过程易崩溃、易残留 1.2GB 文件且缺少反馈，如何加固？
- **选项 A（推荐）**：全套根治：
  1. 修正压缩格式判断，区分 `data.tar.xz` 与 `data.tar.gz` 独立管道；
  2. 宿主若缺少 busybox 自动先从 assets 流式释放，不依赖容器历史状态；
  3. 全程包裹 `try ... finally`，任何异常或用户取消强行清理 `qq-data.*` 与临时解包目录；
  4. 捕获 busybox stderr 输出，并实时在安装详情卡片及 `WhaleLog` 中展示；
  5. 扫描到多个 deb 包时，按修改时间降序展示列表供用户选择，而不是固定 break 第一个。
- **选项 B**：仅修复格式判定崩溃与添加 finally 清理，其余交互保持现状。

### 议题 4：525 个原生图形库的释放性能优化与体积治理
- **问题**：每次启动容器释放 138MB 库并执行 525 次 fork 导致假死，如何优化？
- **选项 A（推荐）**：
  1. 引入「版本印记文件」（记录 APK `versionCode`），只有在首次释放或 App 升级后才执行解压；
  2. 检查目标文件存在且大小一致则跳过；
  3. 用 Java 原��文件属性设置替代频繁 fork `/system/bin/chmod`；
  4. 后续跑 `readelf` 提取 `wrapper.node` 真实依赖闭包，将 525 个文件裁剪至 40 个以内的最小依赖集合。
- **选项 B**：仅做存在性检查跳过，不对依赖集合进行静态裁剪。

### 议题 5：全局原生系统黑框 AlertDialog 沉浸式改造
- **问题**：全仓 41 处 `AlertDialog` 与产品设计语言不合且偶发拦截，如何推进？
- **选项 A（推荐）**：分批替换：
  - 第一批（高频交互）：`CoreManagerScreen`、`VersionScreen`、`BotConfigScreen`、`SettingsScreen` 改用基于现有 `Ui.card` + `Theme` 打造的原生半屏/底部弹出面板（自制 BottomSheet/DialogView）；
  - 第二批：B 站授权、Web 登录与协议编辑页面替换。
- **选项 B**：继续沿用系统原生 `AlertDialog`，仅统一标题与按钮文案。

### 议题 6：`loader.node` 动态链接路径技术债根治
- **问题**：编译期绝对路径 hardcode 违反 P3 原则，何时根治？
- **选项 A（推荐）**：使用本地交叉编译工具链（NDK/WSL clang++），传入 `-Wl,-rpath,'$ORIGIN'` 重新编译 `loader.node`，彻底移除 ContainerService 内在 `/mnt/d/...` 摆放软链补丁的代码。
- **选项 B**：暂时保留该伪造路径补偿，优先做上层功能修复。
