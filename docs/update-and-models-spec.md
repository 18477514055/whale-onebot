# 更新与模型配置：要实现的三件事（用户 2026-11-19 要求）

> 本文只记**要求与做法边界**，不是已完成说明。实现状态见各节末尾的「现状」。

## 1. 设置里要有「检查更新」，而且**两条路分开**

用户原话要点：加「检查更新」，专门用来拉**正在使用的内置机器人**的更新，以及**App 自身**的更新；
**两个更新不要混在一起**；多条路并行（国内有些地方走镜像源更好），做成**多级路由**。

| 通道 | 更新的是什么 | 触发 | 落地形态 |
|---|---|---|---|
| **A. 内置机器人** | 运行端代码/数据（`/input/agent-app` 那一套） | 用户在「运行端」页点检查 | 下载 `runtime-<版本>.zip` → 校验 → 解包 → 切换 |
| **B. App 自身** | APK | 用户在「关于/设置」点检查 | 下载 APK → 交给系统安装器 |

**必须分开的理由**：A 换的是容器里的文件（失败还能回滚到旧 rootfs），B 换的是 App 本身（失败要重装）。
混在一起就等于把"回滚容易"和"回滚困难"两件事绑一起。

**多级路由**（按顺序尝试，失败自动降级，全程可在面板看到用了哪一条）：

1. 用户自填的**自定义源**（面板可填 URL / 镜像）；
2. 本项目仓库的 **release 资产**（GitHub）；
3. 国内**镜像源**（`ghproxy` 类反代 / 自建对象存储），逐条超时后回退；
4. 全部失败 ⇒ 明确报"取不到索引"，**不产生假进度**。

现状：只有 A 的**索引 + 下载器**（`runtime-index/`、`RuntimeDownloader`），没有"检查更新"入口；
B 完全没有；多级路由没有。

## 2. 一条龙：下载完**自动装进容器**

用户原话：「已知限制的第一条不太好……让下载后自动安装进容器，一条龙服务进行，不是每个人都和我们一样能折腾的。」

要做到：**点一次 → 下载 → 校验 sha256 → 解包到 `rootfs.new` → 四项可用性检查 → 两次 rename 切换
→ 保留一份 `rootfs.old-<时间>` → 自动重启容器**。中途任何一步失败 ⇒ 保留旧 rootfs，报告原因。

现状：`ContainerService.unpackRootfs()` 已经会按顺序找包、先解到 `rootfs.new`、四项检查、再换；
**缺的是把"下载完成"接到"解包安装"这条线上**，以及失败时的用户可见说明。

## 3. 模型按用途分开配，且知识库/记忆库的向量与重排**各自独立**

用户要求：
- 按用途分：聊天、记忆整理、语音（ASR/TTS）、画图……各自选 provider + model + key（**已有**：`api` / `memory` / `asr` / `tts` / `imageGen`）；
- **内置知识库与记忆库所需的向量模型、重排模型**也要能配，而且**不要默认复用同一个** ——
  知识库是"文档检索"，记忆是"对话召回"，两者语料与召回目标不同，混用会同时拖累两边。

要新增的四组键（名字待定，倾向）：

| 用途 | 键 | 说明 |
|---|---|---|
| 知识库向量 | `knowledge.embed.provider` / `.model` / `.key` | 文档切块后的向量化 |
| 知识库重排 | `knowledge.rerank.provider` / `.model` / `.key` | 检索结果重排 |
| 记忆向量 | `memory.embed.*` | 对话记忆召回 |
| 记忆重排 | `memory.rerank.*` | 记忆召回重排 |

**迁移规则**：老配置里已有 `memory.provider` / `memory.model` / `memory.useChatModel`，
迁移时以它作为**记忆向量**的初值；知识库那两组留空 ⇒ 明确提示"未配置，将退回关键词检索"，
**不要**偷偷拿记忆的模型顶上（那正是要拆开的原因）。

现状：`memory.*` 有一组；`knowledge.*` 只有开关/切片参数（`enabled` / `dir` / `maxResults` /
`chunkChars` / `overlapChars`），**没有任何模型键** —— 这就是要补的地方。
