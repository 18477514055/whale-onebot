## 合并转发实测（2026-11-23，真机）

真机上确实有合并转发（在 8 个群里各拉 100 条历史，命中 3 条），而 `get_forward_msg` 对它们**恒 1500** ——
这与日志里的 `read_forward 1500 ×15` 和 stdout「展开合并转发失败」176 次完全对得上。用
`debug_forward_probe` 对同一条真实转发逐个试内核方法：

| 调用 | 结果 |
|---|---|
| `getMultiMsg(peer, msgId, resId)` | **result: 5，msgList 长度 0**（即 E11 记的「恒 result=5」，6ms 返回） |
| `fetchLongMsg(peer, msgId)` | 立即 resolve，**返回对象没有任何键**（void 形态），1ms |
| `fetchLongMsgWithCb(peer, Number(msgId))` | **result: 4** + errMsg，9ms |
| `fetchLongMsg` 后等 1.5 秒**再读一次** `getMultiMsg` | 仍然是 **result: 5 / msgList 0** |

⇒「先 fetchLongMsg 拉下来、再让 getMultiMsg 读缓存」这个假设**已被证伪**。剩下唯一没试的是
`addKernelMsgQueryListener` / `addKernelMsgNotifyListener` 这两个我们尚未订阅的监听器
（长消息可能通过它们回调）—— 那要先订上监听器再驱动一次 fetch，属独立一轮的活。

**用户可见影响**：别人转发聊天记录时，机器人只能看到「有一段合并转发」这个占位，看不到里面内容；
其余消息不受影响。`debug_forward_probe` 留在协议端（只读、令牌门），接手者可直接复现上述三条。

## ① 体检补一条真缺陷：容器重启后机器人不会自己回来（已修）

- **现象**：`停止容器 → 启动容器` 之后，容器明明 ready 了，QQ 协议端（13800）却一直没人听，
  `container.log` 里**没有**那句 `容器就绪 → 自动启动机器人`。
- **根因**：`ContainerService.autoBotStarted` 是 `static volatile`，跨「容器停止/启动」保留为 true
  ⇒ 同一个 App 进程里第二次起容器时，自动拉起机器人的条件恒假。
  真机时间线（`grep 容器就绪`）：04:36/04:38/04:40/04:43/04:46（每次重装 APK、进程重启 → 会触发），
  05:10:18 与 05:11:00（同一进程两次 boot）→ 修复后两次都触发。
- **改法**：`boot()` 里 `proc = pb.start()` 之前复位 `autoBotStarted = false`（它本来只想保证
  「每次容器就绪只拉起一次」）。改动一行 + 注释写明原因。
- **真机验证**：同一进程内两次 boot 都打出 `容器就绪 → 自动启动机器人`；
  `bot.json` → `phase: agent-running`、uin 100000001、agent pid 19828；OneBot 13800 回 `retcode 0`。

## 置顶：从「语义待定」到真机可用（2026-11-23 05:2x）

**先定语义**（这一步以前一直含糊）。内核类型定义（`.tmp/napcat-src/packages/napcat-core/services/`）里只有三类相关方法，全部是**会话级**：

| 方法 | 签名 | 位置 |
|---|---|---|
| `group.setTop` | `(groupCode: string, isTop: boolean): void` | NodeIKernelGroupService.ts:224 |
| `buddy.setTop` | `(uid: number, isTop: boolean): void` | NodeIKernelBuddyService.ts:103 |
| `msg.setContactLocalTop` | `(peer: Peer, isTop: boolean): unknown` | NodeIKernelMsgService.ts:634 |
| `recentContact.setContactListTop` | `(peer: Peer, isTop: boolean): unknown` | NodeIKernelRecentContactService.ts:9 |

⇒ **群消息级置顶在 NT 内核里根本没有方法**；「置顶」只能是会话置顶。于是按最干净的签名（groupCode 是字符串、参数就是布尔）实现：

- 动作 `set_group_top`，参数 `{group_id, enable?}`（`enable` 缺省 true；与 `set_group_admin`/`set_group_whole_ban` 同一套布尔归一）
- 成功返回 `{group_id, enable}`；原生拒绝走 `checkResult` → `1500`，不会假装成功
- 能力表只在 `group.setTop` 存在时才报这个动作（`has(this.group, 'setTop')`），旧内核上不出现

**真机实测（23049RAD8C，debug，真号 100000001）**：

| 调用 | 结果 |
|---|---|
| `get_supported_actions` | **91 个动作**，含 `set_group_top` |
| `set_group_top {group_id: 200000002, enable: true}` | **retcode 0**，data `{group_id: 200000002, enable: true}` |
| `set_group_top {group_id: 200000002, enable: false}` | **retcode 0**，data `{group_id: 200000002, enable: false}` |
| 同时刻 bot.log | 没有 `[native-rejected]` 相关行 |

**私聊置顶（`set_friend_top {user_id, enable?}`，同轮补上）**：

内核两个候选都试了，结果很清楚：

| 调用 | 真号实测 |
|---|---|
| `msg.setContactLocalTop({ chatType: 1, peerUid: '<uin>' }, true/false)` | **retcode 0**（置顶与取消各一次，返回 `via: msg.setContactLocalTop`） |
| `buddy.setTop(<uin>, …)` | 未走到（第一条就成功；它的 `uid: number` 语义本来就不确定） |
| 对**受保护账号**（OWNER_UIN 100000002） | **1403 Protected account** —— 我们自己的边界闸生效，不是内核失败 |

实现上按顺序试这两个候选，返回**实际生效的那条**（`via`），不是把没验证的形状说成已验证；
两条都被拒就抛 1500 并把每次的 retcode/原因带回来。

★ **诚实的边界**：内核**没有「读回某个会话是否置顶」的接口**（四类 set 都没有对应 get），所以这条的验证是
「原生受理且不报错」，不是「回读确认排序变了」。要么由人在 QQ 侧眼看，要么以后去读 MMKV/DB —— 都不做，
免得把「返回 0」说成「已经置顶生效」。
★ 私聊置顶（`buddy.setTop` 需要 number 型 uid、`msg.setContactLocalTop` 需要 `Peer{chatType, peerUid}`）
**未做**：Peer 的 chatType/peerUid 取值在真号上还没实测，硬接等于把 1404 换成一个更难查的 1500。
