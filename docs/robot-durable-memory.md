# Managed robot memory boundary

One robot can use many accounts and protocols. Sharing is **not** accomplished by pointing their agent data directories at each other. Each worker still owns its chat history, handoffs (including last replies), living-memory turn log, identity/permission data, sessions and outbox. Nothing imports data from an old profile. Standalone workers continue using their original storage.

The launcher supplies `QQ_AGENT_ROBOT_ID`, `QQ_AGENT_BINDING_ID`, `WHALE_AGENT_PLATFORM`, a private `QQ_AGENT_DATA_DIR`, and an absolute `QQ_AGENT_DURABLE_DIR`. Default `QQ_AGENT_MEMORY_SCOPE=robot`: the latter directory is `<manifest-directory>/durable/<robot-id>`. For an opted-out binding the launcher sets `QQ_AGENT_MEMORY_SCOPE=binding` and uses `<worker-data>/durable`. The database checks its recorded owner on open; pointing a different robot (or changing scope in place) at an existing store is an error. Use a local filesystem with working SQLite locks. Switching scopes does not copy, erase or migrate data; returning to a previously used scope returns to its contents.

| Data | Runtime behavior |
|---|---|
| Long-term member impressions and relationship counters | Same protocol + same peer ID refers to one person; appends and interactions use SQLite read–modify–write transactions. The model's `memory_query` can also explicitly recall another protocol's summarized impressions (e.g. `qq:42`); identical numeric IDs on different protocols are never treated as one person. Source chat IDs are binding-qualified; `perChat` and hide-private filters still apply. No automatic cross-protocol identity linking. |
| Persona mood, energy, last interaction | Stored per persona template/name within the selected scope. Same persona on QQ and Bilibili sees the same state when the humanization feature is enabled. Bot persona configuration is distinct from this changing state. |
| Lightweight knowledge | `writeKnowledgeFile`/console file routes persist named `.md`/`.txt` documents in `durable.sqlite`. `knowledge_search` uses committed revisions to refresh an already-running reader. A managed worker ignores arbitrary `knowledge.dir` overrides. |
| Multi-library knowledge | Library definitions live in the same owner-checked SQLite catalog. Register existing directories under `<durable-dir>/corpus/` (e.g. `corpus/game/`) and rebuild via `buildIndex`; `kb_search` uses `<durable-dir>/library-index.sqlite`. Edit the object returned by `loadLibraries` or a spread of it; `saveLibraries` rejects stale revisions instead of losing edits. Rebuilds use one index transaction: another reader sees the previous complete index until commit; a failed rebuild rolls back. Concurrent writers may get a busy error after five seconds and can retry. Embedding credentials and optional native extensions are not shared. |

**Existing QQ primary (`whale-1`) companion exception.** The primary remains running in its own profile. The enrolled Bilibili child receives `QQ_AGENT_LEGACY_COMPANION=1` and the path to the primary's `config.json`. Only non-isolated companions get these live read-only views: the newer saved state of the same persona; a keyword lookup with an explicit namespaced `userId` such as `qq:42` of that one person's group-sourced impressions; default-folder Markdown/text knowledge when enabled; and exact-text keyword hits in explicitly enabled entries of the existing multi-library index. No bulk people list, private/mixed-origin impressions, messages, handoffs, ACLs, administrative tools, custom corpus paths or external embedding calls are projected. `perChat` hides all legacy impressions. Missing/redirected files are skipped; WAL-mode primary indexes are skipped to avoid creating SQLite sidecars. Returned legacy hits do not become managed records. New companion writes go to managed storage and are **not written back into the standalone QQ profile**. Removing the companion leaves the primary untouched.

Offline regression: `node --test test/robot-memory.test.mjs`. It runs separate processes using only generated fixtures, checks live reads, concurrent increments, restart, rollback, owner mismatch, isolated binding/robot negatives, and the distinction between account-local handoffs and shared facts. The multi-library test exercises the offline keyword path, not an external embedding service.
